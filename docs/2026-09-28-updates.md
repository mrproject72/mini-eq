## Smooth dropdown highlight: the CSS selector was targeting the wrong node

The highlight code was correct — `smooth_menu.add_css_class("smooth-on")` was
firing (confirmed: `cls=["popup","smooth-on"]`) — but the CSS rule was

```css
button.smooth-on { ... }   /* NEVER matched */
```

`gtk4::MenuButton` renders as a **`menubutton`** CSS node wrapping an
internal `button`, so the class lands on `menubutton.smooth-on` and a
`button.smooth-on` selector cannot match it. Fixed to target both:

```css
menubutton.smooth-on > button,
menubutton.smooth-on button { ... }
```

**Gotcha worth remembering:** in GTK4 a `MenuButton` is NOT a `button` node.
Any CSS aimed at a menu button must use `menubutton`, or `menubutton > button`
to reach the visible control. Verified with a `css_name()` diagnostic.

## Auto-Safe reverted to feed-forward: live-driven preamp CLIPS

**The hybrid added one commit ago was wrong and has been removed.**

**Decisive observation from the user:** "the issue occurs when I switch
the monitor on, if it's off the auto-safe is doing its job." That maps
exactly onto the two code paths — monitor off falls back to the curve-only
value (correct), monitor on uses the live-driven value (clips).

**Why a live-driven preamp cannot work here:**

| constraint | value |
|---|---|
| Auto-Safe tick | **33 ms** |
| Hard limiter in the PipeWire filter chain | **none** |
| Program transient length (drums, plucks) | **1–10 ms** |

A transient passes through and clips **before the feedback loop can even
observe it**, let alone correct. There is nothing downstream that stops it.
Widening the attack only makes the steady-state louder and the clipping
worse.

**Feed-forward is the only thing that can prevent this.** The curve peak
is known *in advance* from the EQ settings, so the preamp is set before
any audio arrives. That is why upstream does it this way, and why the
monitor-off path behaved correctly.

**What was removed:** `hybrid_auto_safe_preamp_db`, `AUTO_SAFE_ATTACK`,
`AUTO_SAFE_RELEASE` and their 5 tests. Auto-Safe is back to
`auto_safe_preamp_db(raw_peak, target)` — upstream parity.

**What was kept (all still live):**
- Numeric label shows the real output peak in dBFS when the monitor runs,
  or `EQ max +X.X dB` when it does not
- Status LED goes live with the monitor
- The warn/blink flag prefers the live peak

So the monitor informs the **display**, never the **preamp**.

**If loudness-under-Auto-Safe is ever revisited**, the prerequisite is a
sample-accurate limiter in the filter chain — not a faster UI loop. The
PipeWire filter-graph builtin plugin would need to provide one; without it
this tradeoff is unavoidable.

## Auto-Safe is now hybrid: live-driven, floored at the curve worst case

**Problem:** upstream (curve-only) Auto-Safe assumes program material hits
**0 dBFS exactly at the band you boosted hardest**. Real material does not,
so engaging Auto-Safe dropped the volume far more than necessary — a +6 dB
boost forced -7 dB of preamp even on material peaking at -14 dBFS,
landing the output at -21 dBFS.

**New: `hybrid_auto_safe_preamp_db`** (`window_headroom.rs`)

```rust
pub fn hybrid_auto_safe_preamp_db(
    current_preamp_db: f64,
    live_peak_dbfs: Option<f64>,
    monitor_running: bool,
    curve_raw_peak_db: f64,
    target_dbfs: f64,
    attack: f64,   // AUTO_SAFE_ATTACK  = 0.50
    release: f64,  // AUTO_SAFE_RELEASE = 0.05
) -> f64
```

Decision table:

| monitor | live peak | result |
|---|---|---|
| off | any | `curve_safe` — **upstream behaviour preserved** |
| on | none / NaN (silence) | **HOLD** current preamp |
| on | finite | `clamp(current + (target - live) * alpha, curve_safe, 0)` |

**Why HOLD on silence matters:** falling back to `curve_safe` during quiet
passages would duck the volume every time the material went quiet. Holding
avoids that entirely.

**Why `curve_safe` is a floor, not a ceiling:** it is the *maximum*
reduction that could ever be required (it already assumes 0 dBFS input),
so reducing further is never justified. The hybrid is free to sit above it
— which is precisely the loudness that was being thrown away.

**Attack/release** (`0.5` down / `0.05` up per tick) so the loop protects
headroom quickly but relaxes slowly, avoiding audible pumping on dynamic
material.

**Critical implementation detail:** `Analyzer::take_window_peak()`
**consumes** the value (resets it to 0). The tick now reads
`monitor_peak_dbfs()` **once** at the top and reuses it for Auto-Safe, the
live label and the warn flag. Reading it twice in one tick would return
`None` the second time.

**Also this round:** the status LED now goes live when the monitor is
running (`HeadroomPanel::led_state`, decoupled from `state`). `state`
still gates the Set Safe button and must stay curve-based — that button is
about "your EQ boosts too much", a property of the settings, not of
whatever happens to be playing.

**Tests added (5):** upstream fallback without monitor; holds on silence
and on NaN; demonstrably louder than curve-only; never above 0 dB nor
below `curve_safe`; attack strictly outpaces release.

## Peak label was showing EQ boost, not output level (two symptoms, one cause)

**Reported:**

   until a slider is moved.
2. Other programs' dB levels are far higher than what the app shows as its

boolean and never displayed it.

**Fix:** `HeadroomPanel::apply_live_peak(live_dbfs: Option<f64>)`, called
each tick right after `update_curve_peak`:

| monitor | label | tooltip |

| off | `EQ max +6.0 dB` | "Maximum boost of the EQ curve — not a live level. Turn on Monitor to see the real output peak." |

**Deliberately unchanged:** `update_curve_peak` still drives Auto-Safe and

## Smooth = band-count control (resolved). Q was the wrong parameter.

**User's final definition of a smooth change:** "the minimum should mimic
the bell effect confined to one band; when width increases the bell effect
expands through other frequencies but it ends at the base within the other
bands level set, never lower, so that the curves stay rounded with no waves
effect."

**Root cause of the whole saga: Q is a filter-domain parameter; the user
was describing a curve-domain property.** Every attempt to express the
requirement as a Q/width kept losing the meaning, which is why each
iteration came out wrong.

### What shipped

The slider is now a **band-count** control (Gaussian sigma in bands), not
a bell-width control:

| slider | bands that move |
|---|---|
| `SMOOTH_SPREAD_MIN_BANDS = 0.45` | **1** — only the dragged band |
| `SMOOTH_SPREAD_DEFAULT_BANDS = 0.8` | 3 |
| `SMOOTH_SPREAD_MAX_BANDS = 3.0` | 9 |

Bell Q is **derived** from the spread and floored at the bridging width, so
the bump stays rounded instead of collapsing into a spike:

```rust
pub const SMOOTH_BRIDGE_WIDTH_OCT: f64 = 1.3;   // min width that bridges adjacent bands
pub fn smooth_bell_q(spread_bands: f64, spacing_oct: f64) -> f64;
pub fn smooth_kernel_weights(center, delta_db, sigma, band_count) -> Vec<(usize, f64)>;
pub fn band_spacing_oct(bands: &[EqBand]) -> f64;
```

Kernel drop threshold raised from 2% to **10%** — at 2% the tails dragged
7 bands at minimum width, which is what the user saw as "many other bars
rise". At 10% with sigma 0.45 the kernel is empty: exactly one band moves.

Verified the peak lands on the dragged band's own frequency at minimum
spread (119.1 Hz vs f0 119.2 Hz — grid resolution).

### Key insight recorded for future work

The user's "ends at the base within the other bands level set, never
lower" is the definition of **monotone interpolation** (Fritsch–Carlson /
PCHIP): no overshoot, so waves are impossible *by construction* rather
than by tuning. Verified: a monotone spline through the band control points
gives 0 extrema at every spread.

**Hard constraint:** the audio is a sum of PipeWire biquads; the filter
chain cannot compute `max()`, so the audio cannot literally *be* a spline.
The implementable equivalent of the "never lower" rule is a **gain clamp**:
each neighbour is pulled toward the dragged level but clamped so it never
drops below the level that band already held.

### Superseded approaches (do not revisit)

| attempt | why it failed |
|---|---|
| Fixed `Q = 0.55` | measured on one isolated bump; wrong for multi-band sums |
| Width in octaves `0.5..4.0` | allowed the underlap zone -> 11 troughs |
| Width floored at 1.05 oct | still 9 extrema; 2% kernel tail dragged 7 bands |
| `sigma = width / spacing` | coupled the two so narrow-local operation was unreachable |

### Tests

88 pass. Key regression guards:

- `test_min_spread_moves_only_the_dragged_band` — kernel is empty at min spread
- `test_spread_scales_participating_bands_without_waves` — participation
  scales 1 < 3 < 9 AND extrema <= 2 at every stop AND peak sits on the
  dragged band's frequency at minimum
- `test_smooth_kernel_weights_gaussian_falloff` — symmetry, exact values,
  centre excluded, degenerate inputs couple nothing

## Width now controls HOW MANY BANDS MOVE (the correct semantics)

**User correction:** "the widening/narrowing means that the smoothness
should be applied only to a smaller/larger portion of bands. when I set
width to 1.05 there are still many bands involved in the movement, which
is the opposite of what we want."

The previous design had the knob controlling only the **bell's spectral
width**, while the coupling kernel was a fixed `+/-2 bands` regardless. So
the knob never changed participation — it just changed how fat each bump
was. Wrong axis.

**New model: one knob drives two things that must move together.**

```
width (oct)  ->  Q          = q_for_smooth_width(width)     [bell width]
             ->  sigma(bands) = width / band_spacing        [participation]
```

Coupling is now a **Gaussian kernel** over band-index distance instead of
the fixed 4-tap table:

```rust
pub fn smooth_spread_sigma_bands(width_oct: f64, spacing_oct: f64) -> f64;
pub fn smooth_kernel_weights(center, delta_db, sigma, band_count) -> Vec<(usize, f64)>;
// weight = exp(-k^2 / 2 sigma^2), tails below 2% dropped
```

**Why the two must be coupled.** Holding the bell fixed while widening the
spread leaves the bells unable to bridge the participating region, which
produces *real* ripple sitting right on the bump — measured extrema at
65, 79, 120, 181, 223 Hz, i.e. exactly the "U shapes" being complained
of. Widening the bell with the spread removes it completely.

**Verified on the stock 10-band layout** (drag band 3 by +6 dB):

| width | Q | sigma | bands moved | extrema |
|---|---|---|---|---|
| 1.05 | 1.35 | 1.05 | 5 | 5 (still bad — excluded) |
| **1.30** | 1.07 | 1.30 | **5** | **1** |
| **1.60** | 0.86 | 1.61 | **6** | **1** |
| 1.90 | 0.71 | 1.91 | 7 | 1 |
| 2.20 | 0.59 | 2.21 | 7 | 1 |
| 2.50 | 0.51 | 2.51 | 8 | 1 |
| **3.00** | 0.40 | 3.01 | **9** | **1** |

So the slider now reads exactly as intended: **left = few bands, tight
local edit; right = most of the spectrum moves together** — and no setting
in the range produces U-shaped troughs.

**New bounds** (derived from live band geometry):

```rust
pub const SMOOTH_WIDTH_MIN_XSPC: f64 = 1.3;   // ~5 bands
pub const SMOOTH_WIDTH_DEFAULT_XSPC: f64 = 1.6; // ~6 bands
pub const SMOOTH_WIDTH_MAX_XSPC: f64 = 3.0;   // ~9 bands
```

**Tests added:** `test_smooth_kernel_weights_gaussian_falloff` (symmetry,
exact Gaussian values, centre excluded, degenerate inputs yield no
coupling) and `test_width_scales_participating_bands_without_waves`
(participation strictly increases min<default<max AND extrema <= 2 at all
three — the direct regression guard for this complaint).

**Note:** `SMOOTH_NEIGHBOR_WEIGHTS` / `smooth_neighbor_deltas` remain in
the tree and tested, but are no longer used by the live smooth path.

## Width control range was wrong: narrowing produced U-shaped troughs

**User observation:** reducing the width made the curve dip into "U" shapes
instead of forming tighter rounded bumps.

**Why that happens — and why it is unavoidable below a floor.** A peaking
biquad with positive gain is *never below 0 dB*; it can only add. So a
"U" trough is not something the filter generated — it is the **absence of
boost in the gap between bands**.

Measured band layout: 10 log-spaced bands, spacing **0.997 oct**. A bell of
half-boost width W covers ~W octaves around its centre. When `W < spacing`
neighbouring bells cannot reach each other, so between every pair of band
centres there is a region where neither contributes and the summed curve
falls back toward 0 dB -> a U-shaped valley.

So narrowing does **not** tighten the bump; it *isolates* it. Valleys are
geometric once width drops below spacing.

**Measured against the real layout** (coupled 5-band bump, extrema counted
across the full spectrum — each extra extremum is a visible wave):

| width (oct) | W/spacing | Q | extrema |
|---|---|---|---|
| 0.50 | 0.50 | 2.80 | **11** |
| 0.75 | 0.75 | 1.89 | **11** |
| 0.90 | 0.90 | 1.56 | **9** |
| 1.05 | 1.05 | 1.33 | ~4 |
| **1.30** | **1.30** | **1.06** | **1** |
| 1.50 | 1.51 | 0.91 | 1 |

**Fix:** the slider no longer exposes the broken zone. Bounds are derived
from the actual band geometry rather than a fixed octave range:

```rust
pub const SMOOTH_WIDTH_MIN_XSPC: f64 = 1.05;   // just above underlap
pub const SMOOTH_WIDTH_DEFAULT_XSPC: f64 = 1.3; // fully blended, 1 extremum
pub const SMOOTH_WIDTH_MAX_XSPC: f64 = 2.0;
pub fn band_spacing_oct(bands: &[EqBand]) -> f64;
pub fn smooth_width_bounds_oct(bands: &[EqBand]) -> (f64, f64, f64);
```

Previously the range was `0.5 .. 4.0`, which allowed the user straight into
the 11-extrema underlap zone — that is exactly what was seen on screen.
Bounds are computed from live band frequencies, so if the active band count
changes the control follows automatically.

Also fixed: the slider now shows its numeric value (`set_draw_value(true)`,
value on the right) — previously it rendered with no visible number.

**Superseded values.** The earlier default of 2.34 oct (Q 0.55) was chosen
from a single-isolated-bump waviness metric and was wrong for multi-band
summation. The old `SMOOTH_BELL_Q = 0.55` remains defined for reference
but is no longer the operating point.

**Tests added:** `test_band_spacing_and_width_bounds`,
`test_smooth_width_default_has_no_inter_band_waves` (asserts the default
yields <= 3 extrema and the floor stays <= 5 — a direct regression guard
against the U-trough regression).

**Design note for future work:** if a *tighter* effect is wanted without
valleys, the correct lever is **how many bands participate** (the coupling
kernel), not the bell width. Narrow + many coupled bands is the worst case
and is now unreachable via the width slider.

## Smooth curve width is now a first-class control (octaves)

**Why:** the `Sin` override pinned Q at 0.55, which gave the right shape but
no way to say "make the curve wider/narrower". Q is also a bad control for
this — smaller means wider, and the number means nothing to the ear.

**Key measurement: half-boost bandwidth is gain-independent.** The span
where the bell sits at least half its peak boost measured identical at
+3 / +6 / +12 / +18 dB (2.34 oct at Q 0.55 in all four cases). That makes
**octaves** an honest control rather than a gain-dependent illusion.

**New API (`src/core.rs`):**

```rust
pub const SMOOTH_WIDTH_MIN_OCT: f64 = 0.5;
pub const SMOOTH_WIDTH_MAX_OCT: f64 = 4.0;
pub const SMOOTH_WIDTH_DEFAULT_OCT: f64 = 2.34;   // == Q 0.55
pub fn q_for_smooth_width(width_oct: f64) -> f64; // table + lerp
pub fn smooth_effective_band(band: &EqBand, width_oct: f64) -> EqBand;
```

Width->Q is not a simple inverse (`width*Q` drifts from 1.44 at Q=3.0 to
1.10 at Q=0.3), so a 15-point table generated by numerical inversion is
used with linear interpolation. Verified round-trip: table 2.50 -> Q 0.5072
-> measured width 2.503 oct; table 2.75 -> Q 0.4498 -> 2.749 oct.

| width (oct) | Q |
|---|---|
| 0.50 | 2.851 |
| 1.00 | 1.407 |
| 2.34 | ~0.55 (default) |
| 4.00 | 0.263 |

**UI:** a `Width` scale (0.50–4.00 oct, step 0.05) added to the output
control row between Smooth and A/B Compare. It is **insensitive until the
Smooth switch is turned on**, since width only means anything for the
override. Value held in `HeadroomPanel::smooth_width_oct` and read live by
the DSP snapshot + gain path, so dragging it re-shapes the curve with no
restart.

**Correction made during this work:** an earlier note claimed "Q 0.55 ==
2.59 oct". That was a mislabelled inversion (the search had converged on
the Q whose width is 0.55 oct, not the width of Q 0.55). The correct value
is **2.34 oct**, now asserted by `test_q_for_smooth_width`.

**Tests added:** `test_q_for_smooth_width` — default inverts to the
sweet-spot Q, strictly monotonic across the range, out-of-range clamps
rather than extrapolates, non-finite falls back to default.

## Smooth override: internal `Sin` wide-bell type replaces the band type

**Problem:** the coupling switch moved neighbour *gains*, but each neighbour
was still a Q~1.5 bell, so you got five narrow humps side by side — the
"waves between bands". Shape, not position, was the cause.

**Measured (waviness = p2p of curve vs its own heavy smoothing, lower is
smoother):**

| Q | waviness |
|---|---|
| 1.50 (default bell) | 2.39 dB — visible scalloping |
| 0.80 | 1.34 dB |
| **0.55 (`SMOOTH_BELL_Q`)** | **~1.14 dB — sweet spot** |
| ideal Gaussian bump | ~1.08 dB |
| 0.40 | 1.20 dB (too wide, climbs again) |

A plain 2nd-order bell at Q 0.55 is within **0.06 dB** of an ideal Gaussian
bump, so no exotic DSP was needed.

**Design (avoids the switch/type naming collision):**

- New `FilterType::Sin = 12` — appended last so existing preset
  discriminants are unchanged. **Not** in `SELECTABLE_FILTER_TYPES`, so it
  never appears in the type dropdown.
- While the **Smooth** switch is ON:
  - every non-`Off` band's *effective* type becomes `Sin` at `SMOOTH_BELL_Q`
  - each fader's type label shows **"Sin"**
  - the editor's **Type** dropdown and **Q** spin are disabled (the override
    pins them)
  - neighbour coupling stays active
- While OFF: everything reverts.

**Key invariant: the override never mutates stored state.** `smooth_effective_band()`
returns a modified *copy*; the fader's own `filter_type`/`q_value` are
untouched, so switching Smooth off restores the user's type and Q exactly.
`Off` bands stay `Off` — Smooth must not switch a bypassed band on.

The override is applied at the snapshot boundary (`fader_band_snapshot` and
the 33 ms tick) so the graph, the peak estimate and the backend push all
see the **same** effective bands — the displayed curve cannot disagree
with the audio.

`Sin` maps to `bq_peaking` and shares Bell's coefficient math exactly
(asserted in tests); only the Q differs.

**Tests added:** `test_smooth_effective_band_override` (type/Q forced,
original untouched, `Off` preserved, Sin == Bell at equal Q) and
`test_sin_is_wider_and_smoother_than_default_bell` (measured waviness of
the coupled stack beats the default-Q bell and lands in the ~1.1 dB regime).

## Smooth switch was inert + startup double-load eliminated

**Bug A — Smooth did nothing.** The `smooth_switch` was constructed and
added to the output control row, but **no `connect_state_set` handler was
ever installed**, so `HeadroomPanel::smooth` never changed and
`gain_request` always saw `false`. Only `auto_safe_switch` had been wired.
Fixed by connecting the switch to the shared `Rc<Cell<bool>>` that
`gain_request` clones.

Reminder for testing: toggling Smooth changes nothing on screen by itself —
it only affects the *next drag/scroll/key* on a band.

**Bug B — audio cut twice at startup.** `apply_live_controls` returns
`Ok(false)` when the live filter node proxy is `None`. The proxy is
captured **asynchronously after** the module load, so the first 33 ms UI
tick hit that path and `update_state_live_or_reload` treated it as a live
push failure → full module unload + reload.

Fix:
- `PipeWireBackend::has_live_node()` added.
- `update_state_live_or_reload` returns early (no reload) while the proxy
  is absent — the module was just loaded with the correct bands.
- The UI push is additionally gated on `has_live_node()`, and the signature
  is left **unpushed** so the next tick retries rather than silently
  dropping a pending edit.

Startup log, before vs after:

```
Filter-chain module loaded              Filter-chain module loaded
Preamp gain set to 0 dB                 Captured live filter node proxy

Filter-chain module loaded

```

Now: 1 load, 0 unloads. A *short* interruption at startup is still

## Smooth (neighbour-coupled) band editing

**Requested:** a smooth increment/decrement that involves the adjacent bands
on both sides, instead of a Bell raising an isolated hump on a flat line.

**Implementation — geometric coupling kernel (`src/core.rs`):**

```rust
pub const SMOOTH_NEIGHBOR_WEIGHTS: [(i64, f64); 4] =
    [(-2, 0.25), (-1, 0.5), (1, 0.5), (2, 0.25)];
pub fn smooth_neighbor_deltas(index, delta_db, band_count) -> Vec<(usize, f64)>
```

Half the influence per step away from the dragged band; out-of-range
neighbours are dropped, never wrapped.

**Wiring (`src/window.rs::gain_request`):** when Smooth is on, the dragged
band's **post-cap effective delta** is applied to neighbours one at a time,
each re-clamped against a fresh `fader_band_snapshot` so the peak cap always
sees the latest state. Because the *effective* (capped) delta is used,
coupling can never smuggle extra level past the headroom budget.

Using incremental deltas also means an independent edit to a neighbour is
preserved — the coupling rides on top rather than overwriting it.

**UI:** a `Smooth` switch was added to the main-window output control row
(state on `HeadroomPanel::smooth`, read via `smooth_enabled()`). Default
**off**, so existing behaviour is unchanged until you turn it on.

Drag band 5 by +6 dB with Smooth on:

| band | 3 | 4 | **5** | 6 | 7 |
|---|---|---|---|---|---|
| gain | +1.5 | +3.0 | **+6.0** | +3.0 | +1.5 |

**Tests added:** `test_smooth_neighbor_deltas` (symmetry, edge drop-off,
single-band, zero-delta) and `test_smooth_coupling_shape_and_cap` (the
composed couple+cap loop: expected fractions, monotonic decay away from the
dragged band on both sides, raw peak inside the budget, Set Safe reachable).

**Also this session (UI refactor):** headroom controls moved into the main
window output control row (`Auto-Safe | Smooth | A/B Compare | Preamp |
peak meter | Peak label | Set Safe`); the sidebar page is now **Output**
(device settings only, `PAGE_OUTPUT`); the blinking clipping alert moved off
the header icon onto the **Set Safe** button. Two GTK gotchas fixed: widgets
must be left unparented before reparenting (`gtk_box_append` assertion), and
the peak meter's fixed 260px minimum had to shrink to 90px + hexpand to
avoid an `AdwToolbarView exceeds AdwApplicationWindow width` warning.


## Shelf-stack runaway fixed: fader gain path was bypassing the peak cap

**Symptom (reported):** setting two Hi-shelf bands and sliding one up dragged
the whole curve past the limits ("like an n-times response"); Auto-Safe
pinned the preamp at its floor and Set Safe could not recover. Bell worked
fine. Hi-pass/Band-pass appeared to do nothing.

**Root cause 1 — the fader never asked permission.** `WindowBandFader::new`
installed a *no-op* gain callback:

```rust
Box::new(move |idx, gain| { let _ = (idx, gain); })
```

So `clamp_gain_for_peak` was only reachable from the band editor's gain
**spin**. Every fader **drag / scroll / keyboard / zero** wrote `gain_db`
directly and skipped peak safety entirely. This is why the previous session's
clamp "didn't fix it".

**Root cause 2 — the budget was physically impossible.** Live `pw-dump` of
the running filter-chain showed the Hi-shelf plateaus coincide at high
frequency and *add*: raw curve peak ~**+48 dB** (up to ~+59 dB with more
bands) against a **−24 dB** preamp floor. Set Safe asks for
`0 − peak − 1`, i.e. ~−49..−60 dB, which clamps straight back to −24.
Unreachable by construction. Bells are narrow/localised so they never
crossed the floor — matching "Bell works fine".

**Fix — owner-authoritative gain request (`src/band_fader.rs`,
`window_band_fader.rs`, `window_layout.rs`, `window.rs`):**

- `gain_changed_callback` is now `Option<Rc<dyn Fn(usize, f64) -> f64>>`.
  The fader *requests* a gain and applies what the owner *returns*.
- Handlers clone the `Rc` and **release the borrow before calling**, because
  the owner re-enters the fader (`edit_fader`) — a nested `borrow_mut`
  would panic.
- `window.rs` builds one shared `gain_request` closure used by BOTH the
  faders and the editor spin, so all sources obey one cap.
- The old no-op no longer type-checks: the compiler now enforces that every
  fader gets a real clamping callback.

**Fix — widened the headroom budget (option 2, `src/core.rs`):**

- `EQ_PREAMP_MIN_DB`: −24.0 → **−36.0**
- `MAX_SAFE_RAW_PEAK_DB`: 23.0 → **30.0**
- Budget invariant now documented and asserted:
  `EQ_PREAMP_MIN_DB <= AUTO_SAFE_TARGET_DBFS - MAX_SAFE_RAW_PEAK_DB`
  (−36 ≤ −31, leaving 5 dB slack for estimation/rounding).
- Removed hardcoded `-24.0` literals that would have silently desynced the
  floor: `pipewire_backend::set_preamp` and the `window_headroom` preamp
  `Adjustment` now use the shared constants.

**Measured, user's exact sequence (bands 7,8 = Hi-shelf; band 9 bell +12,
band 8 +12, band 7 +20):**

| step | old cap (23 dB) | new cap (30 dB) |
|---|---|---|
| band 9 bell +12 | +12.0 | **+12.0** |
| band 8 shelf +12 | +9.3 (clamped) | **+12.0** |
| band 7 shelf +20 | **+0.0 — dead fader** | **+3.6** |
| raw peak | 22.99 dB | 29.96 dB |
| preamp needed | −23.99 (at floor) | **−30.96 (5 dB slack)** |

**Not a bug — Hi-pass/Lo-pass/Bandpass/Notch/Allpass ignore the gain
slider.** Upstream's formulas for those types contain no `gain_a` term;
gain is mathematically irrelevant. Verified against upstream `core.py`
formula-for-formula. Shelves/Bell do use gain.

**Tests added (`src/core.rs`):**
- `test_preamp_budget_invariant` — floor can always reach target minus cap.
- `test_user_shelf_stack_is_not_a_dead_fader` — acceptance test for the
  reported sequence: no step refused outright, raw peak grows each step,
  stays inside the cap, Set Safe stays reachable.
- `test_set_safe_can_fix_two_shelf_stack` — uncapped stack exceeds the
  floor (the bug); capped stack lands on −1 dBFS (the fix).

**Verification:** `cargo fmt --check` clean, `cargo clippy --all-targets --
-D warnings` clean, **79 tests pass**. App restarted on the new build:
one PID, one filter-chain group, zero errors/warnings/panics, Auto-Safe
holding the curve at −1 dBFS.

**Operational note:** the earlier "still reproducible" report was against a
**stale binary** — the running process started 08:45:36 but the fix was
built 09:17:12. Two `mini-eq` PipeWire *clients* (111, 143) are normal:
same PID, two connections (main loop + filter-chain/monitor), and only one
filter chain, so no double processing. Always confirm

## Headroom/Auto-Safe peak estimate no longer clamped (upstream parity)

**Symptom (left as an open probe from the 2026-09-27 session):** with several
Hi-shelf bands boosted to +20 dB, Auto-Safe pushed the preamp to its −24 dB
floor yet the estimated peak after compensation still read +36 dB — the
clipping warning could never clear.

**Root cause:** `estimate_response_peak_db` sampled the curve through
`total_response_db_at_frequencies`, which applies the *graph-display* clamp
(`GRAPH_DB_MIN-12 .. GRAPH_DB_MAX+12` = −36..+36 dB). Four stacked +20 dB
shelves truly peak at ~+84 dB, but the estimate saw only +36 dB, so
`auto_safe_preamp_db` computed a target from a masked number. Upstream
avoids this by calling `total_response_db_at_frequencies(..., clamp_output=False)`
inside `estimate_response_peak_db` (core.py:1029).

**Fix (`src/core.rs`):**
- Added `total_response_db_unclamped()` (the raw dB computation) and
  `total_response_db_at_frequencies_unclamped()`.
- `total_response_db()` is now the clamped wrapper (graph rendering
  unchanged: `window_graph.rs`, `window_autoeq.rs` still get clamped values).
- `estimate_response_peak_db()` now uses the **unclamped** path, matching
  upstream `clamp_output=False`.

**Test:** replaced the throwaway `hishelf_autosafe_probe` with
`test_estimate_response_peak_db_is_unclamped` — asserts the 4×HiShelf peak
exceeds the +36 dB display clamp, a single +20 dB shelf measures ~23.5 dB,
and Auto-Safe correctly pins to `EQ_PREAMP_MIN_DB` (residual over-target is
expected: the preamp range cannot absorb +84 dB of boost, but the caller now
sees the real number).

74 lib tests pass, clippy clean, fmt clean.
